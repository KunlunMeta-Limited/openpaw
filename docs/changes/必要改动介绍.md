## 3. 逐项详述

### N1 engine-host CLI 接线 —— 必须

- **改动内容**：`cli.rs` 新增 `--engine-host`、`--engine-host-hostname`(默认 `127.0.0.1`)、`--engine-host-port`(默认 `0`)、`--provider`、`--home`、`--workspace`（均由 `engine-host` feature 门控）；`main.rs` 新增 Host 启动分支（与 `--sidecar` 互斥、退出码 2）；`crates/openpaw-cli/Cargo.toml` 新增 `engine-host` feature、可选依赖 `openpaw-engine-host`；`tests/help_snapshot.rs` 断言三个旗标出现在 root help。
- **改动原因**：AI Office 联调链路为 `AI Office → Action Gateway → openpaw engine-host → AgentLoop → Provider`，Host 进程必须由 CLI 拉起。工作区启动脚本 `start-demo-native.ps1` 的实际调用为：
  `openpaw --engine-host --engine-host-port <port> --provider <p> --home <home> --workspace <ws>`，并由脚本导出 `OPENPAW_PROVIDER`、`OPENPAW_OPENAI_MODEL`、`OPENPAW_OPENAI_BASE_URL`、`OPENPAW_ENV_FILE` 等子进程环境变量。
- **方案与取舍**：保留 CLI 侧接线与 feature 隔离（默认 `default = []`，默认依赖树不含 axum，已用 `cargo tree -p openpaw-cli --no-default-features` 验证）；不在 CLI 内实现任何 Host 协议细节。
- **影响面**：新增用户可见参数；`engine-host` 未启用时三个旗标不存在（帮助快照同时验证这一点）。
- **验证**：`cargo test -p openpaw-cli --features engine-host`、`--features sidecar,engine-host` 均通过（含 `help_snapshot` 4 用例）。

### N2 provider 解析回到进程环境变量 —— 必须

- **改动内容**：`main.rs` 新增私有 `resolve_provider`，优先级 `--provider` > `OPENPAW_PROVIDER` > 密钥存在性（先 `OPENAI_API_KEY` 后 `ANTHROPIC_API_KEY`）> 本地 echo 回退；显式选择未知 provider 或真实 provider 缺密钥时输出英文三段式错误并以退出码 2 结束；回退到 echo 时向 stderr 输出一行提示。`chat.rs` 按 provider 名从进程环境读取密钥构造 provider。
- **改动原因**：修正"provider 被硬编码为 `mock`"这一历史缺陷——即使机器上已配置真实密钥，`openpaw chat` 与 Host 也会进入离线回显模式；同时保持"零配置可运行"（无密钥时仍可 echo）。
- **方案与取舍**：
  - 采用 **`main.rs` 内约 50 行同步函数**，不引入配置模块、不读取配置文件、不新增依赖；
  - 保留退出码 2 表示"配置错误"、1 表示"运行错误"的既有语义；
  - 显式选择真实 provider 但缺密钥时**失败**而不是静默回退，避免把用户请求发到非预期后端；
  - `OPENPAW_PROVIDER` 缺密钥时回退 echo 并提示，保持脚本兼容性。
- **影响面**：`chat` 与 `--engine-host` 的 provider 来源明确为进程环境变量；不再存在 `.env` 自动加载这一隐式来源。
- **验证**：`cargo test -p openpaw-cli --features engine-host` 中 `chat_unknown_provider_fails_with_three_segment_error`、`chat_two_turns_and_session_persisted` 通过。

### N3 transcript 写入失败必须非零退出 —— 必须

- **改动内容**：`chat.rs` 中三处 `let _ = writer.append(..)`（用户消息、助手消息、工具结果）改为 `if let Err(error) = ... { return report_persistence_error(...) }`，错误提示为英文三段式（what/why/next），返回 1。
- **改动原因**：session JSONL 是会话的唯一持久事实源。旧实现忽略写入错误，磁盘满、权限变化或句柄异常时 CLI 仍返回 0，用户会在"对话成功"的假象下丢失全部记录。
- **方案与取舍**：只在写入失败时中止当前会话并返回非零，不做重试、不改 JSONL 格式、不改索引失败的处理策略（SQLite 索引仍是"尽力而为 + 警告"，因为它只影响检索覆盖率，不影响事实源）。
- **影响面**：出错路径提前退出；成功路径与文件格式不变。
- **验证**：成功路径由 `chat_two_turns_and_session_persisted` 覆盖；失败路径暂无自动化注入（见第 6 节残留项）。

### N4 sidecar 到达顺序确定化 —— 应当

- **改动内容**：`sidecar.rs` 新增 `RequestOrder`（`tools/call` 请求 id 的 FIFO 队列 + `Notify` 唤醒 + 取消出队 `remove` / 完成出队 `complete`）；`call_tool` 先等队列轮次再持既有 gate，并在等待与执行阶段分别对 `RequestContext::ct` 取消做 `select!`；新增 `ArrivalOrderTransport`（约 40 行）包装 rmcp 内建 `AsyncRwTransport`，只在 `receive` 侧登记到达顺序，`send`/`close` 直接委托；新增单测 `cancelled_request_is_removed_from_order_queue`。
- **改动原因**：`docs/devlog.md`（会话 37 / P-90）记录了三客户端实测发现的真实竞态：8 帧 back-to-back 发送后 `memory_set` 返回成功，但同批 `memory_get` 报 `no memory with id`、`memory_search` 空结果。P-90 的处置是加互斥 gate，但**互斥只保证互不重叠，不保证先后**；`tokio::sync::Mutex` 只对"已经到达锁的等待者"公平，两个 handler 谁先到达锁由任务调度决定。因此需要把"客户端发送顺序"变成显式依据。
- **方案与取舍**：三个候选方案对比：

  | 方案 | 实现量 | 到达顺序 | 风险 |
  | --- | --- | --- | --- |
  | A：仅保留基线 gate | 0 | 不保证 | 并发 e2e 仍可能 flaky |
  | B：自研完整 stdio 传输层（收敛前实现） | ≈ 150 行 | 保证 | 自行承担分帧、响应排序、关闭、畸形帧；响应排序对 JSON-RPC 非必需 |
  | C：**装饰器只登记到达顺序（当前）** | ≈ 40 行 | 保证 | 依赖 rmcp 内建 transport 的既有行为 |

  选择 C：到达顺序只在读侧可见，因此只包装 `receive`；分帧、写出、关闭、畸形帧处理全部留在 rmcp 内建实现中，删除约 164 行自研代码与两条并行的 FIFO 结构。
- **影响面**：同一时刻仍只有一个工具在执行；执行顺序由"随机的锁竞争"变为"确定的服务端接收顺序"；不再由本仓库保证响应写出顺序（JSON-RPC 按 id 匹配，客户端不需要该保证）。
- **验证**：`cargo test -p openpaw-cli --features sidecar` 通过，含 e2e `sidecar_concurrent_calls_serialize_set_before_get` 与顺序队列单测。

### N5 `config show` 脱敏输出 —— 应当

- **改动内容**：`config_cmd.rs` 只输出 home 存在性、`ANTHROPIC_API_KEY`/`OPENAI_API_KEY` 的"set/not set"以及一行 provider 优先级说明（`--provider > OPENPAW_PROVIDER > key presence > echo fallback`）。
- **改动原因**：新增 provider 推断后，原基线文案 `default provider: mock (offline)` 已成为错误信息；同时配置展示必须继续保证"密钥值永不落屏"。
- **方案与取舍**：不在 `config_cmd` 重复实现 provider 解析（避免与 `main.rs` 逻辑漂移），只说明优先级；`config doctor` 仍转发 `openpaw doctor`。
- **验证**：`cargo test -p openpaw-cli --features sidecar` 通过；人工可核对 `openpaw config show` 输出不含密钥。

### N6 回归测试保留 —— 必须

- **改动内容**：`tests/chat_e2e.rs` 回到基线用例（两轮对话落盘 + 未知 provider 三段式），断言与当前 `main.rs` 文案一致；`tests/sidecar_e2e.rs` 保留 baseline 的并发写读用例；`tests/help_snapshot.rs` 保留 4 个用例（含三个 Host 旗标断言）。
- **改动原因**：N1/N2/N4 是行为改动，必须有可执行证据；同时避免"用新增测试替代契约"。
- **验证**：三套 feature 组合全部通过（见第 5 节）。

### N7 公共项中文 doc 的可见性修正 —— 应当

- **改动内容**：`cli.rs` 的 `pub struct Cli` 上方补 1 行中文 doc；`model_cmd.rs` 的 `pub enum Command` 上方补 1 行中文 doc。
- **改动原因**：治理检查器（`governance/check.py comments`）采用"公共声明前 6 行内必须出现中文注释"的粗规则：
  - `pub struct Cli` 上方 6 行被多行 `#[command(...)]` 属性占满，`///` 不在窗口内；
  - `pub enum Command` 原本靠紧随其后的**中文字符串常量**（`"离线；…"`）误判为"有中文注释"，文案回退为英文后暴露为缺口。
  两者都是检查器可见性问题而非注释缺失，但若不处理，本次回退会让缺口数从 41 涨到 42；补齐后为 **40**（比改动前少 1，因 `lib.rs` 少了一个 `pub mod config_env;`）。
- **方案与取舍**：只补 1 行中文 doc，不动检查器、不做全量注释补齐（`crates/openpaw-cli` 仍有 40 处历史缺口，属既有债务）。
- **验证**：`python governance/check.py comments --root crates/openpaw-cli --language rust --all --report-only` 报告 40 个缺口（报告模式退出码 0），日志 `.git/dsh-comments2.log`。

### 8.4 为什么判"合理"

1. **每条代码改动都对得上具体缺陷或契约**：B02/B03/B05/B06 四类安全与并发阻断 + 流超时 + 空响应 + 重复回复，没有出现重命名、格式化或与本主题无关的重构。
2. **与 CHG-0013 的声明一致**：该 CHG §9.2/§9.3/§9.5/§9.6 的"拟修改符号"（`execute_tools_phased`/`execute_tools_sequential`、Before hook 重排、`AgentLoop` 单活动回合闸门、统一 cancel-vs-operation helper）逐条能在代码里找到对应实现。
3. **新增公共 API 不是为加而加**：`run_turn_with_provider_and_cancel_token` 被 Host 真实调用（`runtime.rs:2184`），`run_turn_with_cancel_token` 被引擎与 Host 测试反复使用；两者都是薄封装（各约 15 行），共用 `run_turn_inner`。
4. **修复都有可执行测试**：上表列出的 18 个测试名（去重后），其中"永不返回/挂起"场景用 validator、guardrail、approval、compaction 四种替身分别覆盖，正是 B06 要求的形态；并行/串行两条路径各有 Replace 与 validator 用例。
5. **取消语义自洽**：内部用 `child_token()`，外部取消向下传播、内部清理不反向污染 Host 终态——这条注释与 Host 侧 `run_turn` 的终态判断一致。

### 8.5 为什么判"不完全是最小改动"

**超出"只修缺陷"范围的三处（建议单独登记或在 CHG-0013 中逐条列明）**：

1. `retry_limit_for_error`：对 `RateLimited`、`503/529`、`RetryableOverloaded` 把重试上限压到 **1 次**。这是**新增重试上限策略**，与 B02/B03/B05/B06 无关；我在 CHG-0011/CHG-0013 的接口与字段表中没有找到登记该策略的行。
2. `Final`-only provider 的事件合成：当 provider 只发 `Final` 时补发 `MessageStart` 与 `TextDelta`/`ThinkingDelta`。它的目的是让 Host 适配器"为每个模型响应分配独立消息编号"，属**新增可观察行为**；非流式 provider 的事件序列因此改变，需要协议/消费端确认（CHG-0013 §6 未单列）。

### 9.2 为什么要改（根因）

| 缺陷 | 机制 | 后果 |
| --- | --- | --- |
| **B10 跨 chunk UTF-8 损坏** | 基线对**每个 HTTP byte chunk 独立**执行 `String::from_utf8_lossy` | HTTP 切分点不是 Unicode 边界：中文（3 字节）/emoji（4 字节）被切开即写入 `U+FFFD`，后续字节到达也无法还原。CHG-0013 §9.10 的真实复现：50K 文本经 Host/JSONL/Gateway/UI 后长度 50004、首个差异在 UTF-16 索引 2823、180K 出现 7 个替换字符 |
| **B11 截断流假成功** | ① JSON 解析失败被静默转成 `Value::Null`；② OpenAI 在 HTTP EOF 时不 flush decoder，直接 `state.finish()`；③ Anthropic 没收到 `message_stop` 也能 `finalize()` | 连接在 25%/50%/99% 处干净断开、最后一帧 JSON 或 tool arguments 被截断时，**部分正文仍被写成 completed 回合**；畸形帧与真实空事件无法区分 |
| **无界缓冲** | 行缓冲、单帧 data、累计正文/thinking/tool 参数都没有上限 | 异常或恶意 Provider 可造成无界内存增长（B16/G08） |
| **tool 参数静默成空** | `arguments` 缺失/非法时 `unwrap_or("{}")` | 模型流被截断时会把**空对象当成合法输入执行工具**，产生错误副作用 |
| **流式正文丢失（数据丢失）** | 基线 `OpenAiStreamState` 不累积文本，`Final.content` 只装 tool_use 块；而 Engine 只把 `resp.content` 回填进 session（`agent_loop.rs` 的 assistant 回填），`TextDelta` 仅作为事件发给 UI | OpenAI 流式路径下**助手正文没有写进会话记录**（长回复尤其明显），UI 有字、session 无字 |
| **错误帧被当空成功** | OpenAI 兼容网关在流中返回 `{"error":{...}}` 时按普通 delta 处理 | 报错被吞成"成功但内容为空"，重试策略也失效 |

### 9.3 逐文件判定

| 文件 | 改了什么 | 为什么必须 | 判定 |
| --- | --- | --- | --- |
| `src/sse.rs`（+550/−119） | ① `SseDecoder` 增加 `utf8_tail`：`feed()` 把上次残留与新字节拼接，只把 `valid_up_to` 之前的**完整前缀**送入行解析，最多保留 3 个未完成尾字节；真非法字节（`error_len().is_some()`）立即失败；`finish()` 遇残留尾部报错。② `Frame.data` 从裸 `Value` 改为 `SseData::{Json, Done}`，畸形 JSON 直接返回 `Error`。③ 新增 `MAX_SSE_LINE_BYTES`/`MAX_SSE_DATA_BYTES`（各 2 MiB）、`MAX_STREAM_ACCUMULATED_BYTES`（16 MiB）、`MAX_CONTENT_BLOCKS`（1024）。④ Anthropic 组装器 `blocks` 由 `Vec` 改 `BTreeMap<usize, _>`，`absorb` 返回 `Result`，`message_stop` 缺失则 `finalize()` 失败，tool 参数必须完整 JSON object | B10（正文损坏）+ B11（假成功）+ 资源上限；这是"所有流式 Provider 共用的字节→文本边界"，错一次就永久破坏用户正文 | **必须**（核心修复） |
| `src/openai.rs`（+331/−33） | ① `finish()` 要求 `[DONE]` 已见且 `stop_reason` 合法；② EOF 时先 `decoder.finish()` 再组装；③ 流内 `error` 帧解析为 `OpenAiStreamError` 并映射稳定错误分类（status/code/type/retry_after）；④ **累积文本并放进 `Final.content`**；⑤ tool_call 严格化：缺 `arguments`/非法 JSON/非 object/缺 id 或 name/`index ≥ 1024` 全部报错；⑥ 累计字节上限 | ②③⑤⑥属 B11；①属终止证据；④是**修数据丢失**（见 9.2 末两行）——Engine 只持久化 `Final.content`，不累积 delta | **必须** |
| `src/anthropic.rs`（+63/−10） | 跟随 `sse.rs` 的签名收紧：`decoder.feed()/finish()` 返回 `Result`、`assembler.absorb()` 返回 `Result<Vec<_>>`，逐帧传播错误并在失败后不再 finalize | 同样的 B10/B11 语义必须对两个 Provider 一致，否则 Anthropic 路径仍会假成功 | **必须**（适配性修复） |
| `src/http.rs`（+4/−0） | 两个 reqwest client 各加一行 `.http1_only()` | 兼容部分 OpenAI 兼容网关/SSE 反向代理不完整的 HTTP/2 协商，避免代理提前重置长连接（重置会直接触发上面的截断路径） | **应当**（工程性修复，理由来自真实联调） |
| `src/mock.rs`（+102/−9） | 新增 `MockMode::DelayedStreamText` + `pub fn stream_text_delayed(text, chunks, delay_ms)`；顺带修 `chunks > 字符数` 时的 `take` 计算（改为 `min(char_count)` + `saturating_sub`）；新增 2 个用例 | 让测试能在**相邻事件之间真实等待**，用于验证 Host 流式期间的取消顺序（属 CHG-0012 的测试设施）；顺带修一处可能 underflow 的切片计算 | **应当**（但归属跨 CHG，见 9.5） |
| `tests/mock_server_contract.rs`（+340/−32） | 真实 HTTP + 受控分块契约：`streaming_long_text_survives_fixed_and_random_http_chunks`（50K/180K 长文、固定与确定性随机 chunk）、`streaming_clean_eof_at_25_50_99_percent_never_finalizes`、OpenAI/Anthropic `terminal_ordering_matrix_rejects_invalid_streams`、`incomplete_tool_arguments_fail_without_final`、`provider_http_data_frame_enforces_two_mib_boundary`、`provider_http_rejects_malformed_json_and_truncated_utf8`、`openai_streaming_error_frame_is_not_an_empty_success` | 这是 B10/B11 唯一能证明"分块不损坏、截断不假成功"的证据形态 | **必须** |

`src/sse.rs` 文件内另有 8 个单测（含固定与随机分块的 Unicode 保真、CRLF/分部 feed、2 MiB 边界），`openai.rs` 1 个（累计上限边界）。

### 9.4 是否最小改动

**可讨论的三处**：

1. `openai.rs` 的 `OpenAiStreamError` + `parse_status` 映射（约 60 行）：把流内错误收敛为稳定分类属**新增语义**，CHG-0013 §6 未单列；不过没有它就无法区分"错误帧"和"空成功"。
2. `sse.rs` 的 Anthropic 资源加固（`BTreeMap` + `MAX_CONTENT_BLOCKS` + 重复/越界 index 拒绝）：属 B16/G08 的资源与协议硬化，超出 B10 本身。
3. `mock.rs` 的 `DelayedStreamText`：为 Host 取消顺序服务，明显属于 CHG-0012 的测试设施，却落在本次 LLM 提交里（跨 CHG 归属）。

**不该省**：`utf8_tail` 增量解码、`SseData::Done`、`Result` 化、EOF 时 `decoder.finish()`、终止证据校验、2 MiB/16 MiB 上限、`Final` 文本累积、tool 参数严格化。

### 9.5 记录问题（需人工确认）

1. **声明的交付物未实现**：CHG-0013 §4 声明新增 `crates/openpaw-llm/tests/fixtures/long-stream-v1.json` 与 `crates/openpaw-llm/Cargo.toml` 的 `sha2` dev-dependency（并连带修改根 `Cargo.toml`/`Cargo.lock`）。实测：`tests/fixtures/` 目录**不存在**，`openpaw-llm/Cargo.toml` 未被修改（dev-dependencies 只有 workspace 的 `tokio`）。
2. **实现采用了另一种可复现机制**：集成测试用进程内 `long_text_utf16(target_units)` 生成 50K/180K 文本、用 `fnv1a64` 做逐字节哈希比对，不落 fixture、不引 `sha2`。从工程角度这**不比原方案差**（版本库不必存 180K 正文、少一个 dev 依赖），但 CHG-0013 必须据此更新，否则"声明 vs 实现"不一致——这正是本轮一直在修的那类记录问题。
3. **`http.rs` 的 `http1_only()` 未登记**：该行为影响所有 Provider 的真实连接方式，我在 CHG-0011/0013 的接口或字段表里没有找到登记行。
4. **本 crate 的注释类改动无 CHG 归属**：`openai.rs`/`anthropic.rs` 的中文注释删除（各 23 行、0 行代码）与 §8.7 是同一口径问题；`crates/openpaw-llm/**` 目前只被 CHG-0013 登记为**代码**改动。提交/PR 前需要补登记。
