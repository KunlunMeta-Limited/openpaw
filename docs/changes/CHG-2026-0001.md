## 2. 变更原因

**现状证据：**T0/T1已审核合入，但主CHG首页与索引曾停留review/待审核/待合入；master已有完成记录，形成矛盾。本次已先在0001补清原交付事实，并将补充修订的方案批准与待实施状态单独登记；索引/工具同步属于获批后的实施范围。现有文件表虽然有理由字段，实际许多行只写“T2生命周期/必改”，不能判断具体方法。当前check.py的load_chg将批准与PR URL绑定，pr_check又拒绝修改多份CHG，分别阻挡“先方案审核、后PR”、前序完成补登，以及用户明确要求的“T3与T0修订共用PR”。仅改文字不会改变这些工具行为。

**目标：**审核人能根据一个明确版本决定改不改、怎么改；实施只在批准范围内；代码、验证、人工决定、PR和合入分别可追溯；下一阶段不会带着未同步的前序状态开始。

**非目标：**不实现Office聊天、Host、T3，不改变运行时API、会话/Todo格式、依赖或沙箱；不降低Linux/Windows全量门禁，不增加macOS，不建立新管理服务或自动批准器。

**方案选择：**延展原检查器与模板，保留十二节及固定framework来源。单纯补表不能避免复发；新建独立系统又会重复解析和审批。项目适配层负责新格式、分阶段检查及历史兼容，原框架快照不动。

**归属与历史：**本次仍完善原T0的工程治理职责，采用原编号的新修订。原交付包含协议fixtures、feature/CI、D12—D30等基线修复；本轮不重新实施这些修复，也不改Office协议或产品范围。原完整内容通过首页链接及第12节保留。

## 6. API 变化

仅治理工具CLI延展：validate/pr-check增加`--stage proposal|implementation|delivery`。proposal校验可审核结构及计划，不要求尚未发生的批准/测试；implementation要求有效方案批准及实际范围；delivery进一步要求T3主任务及显式关联修订各自具备完整证据、交付验收和正确目标。validate默认结构检查，pr-check默认implementation以兼容现有26项注册命令；PR CI显式调用delivery，不以默认行为绕过交付门禁。旧参数和索引/追踪命令保留，不新增approve命令。

方案摘要/逐文件自然语言的充分性、聊天批准来源和产品语义依然由人工判断。工具检查结构、可引用版本、Git范围和状态关系；不把非空姓名/URL当身份认证，不承诺自动证明所有实施行为的时间顺序。

共同交付关系由T3主CHG明确引用0001的准确修订及批准版本；检查器不得仅因发现多个CHG文件就自动认可。纯历史补登与有代码/规则变化的关联修订必须分开校验；关联修订和主任务一样接受独立的方案/交付验收。

## 7. 字段变化

项目CHG增加显式格式版本、提案版本及以下独立事实组：方案批准/实施授权；开发与技术验证；交付人工验收；平台PR；实际合入/完成。第一节是最新状态，第12节追加历史。旧“批准人/时间”只按原记录语义追溯，不自动复制成两次批准。

方案版本绑定真实批准前Git对象或可核验提案版本，登记批准的新commit单独记录。纯审批事实/生成索引维护不自动推翻原方案批准，但必须由精确字段/差异检查证明未夹带实质变化；代码、依赖、权限、方法、验收变化则重审。PR批准后的元数据尽量在下一阶段补登，避免推新commit使平台批准失效。

逐文件表采用第4节准确结构列；文件/操作/必要性分别填写，不从说明猜路径；本修订全部必改，无开放式条件文件。重要风险仍使用保护表，不依赖删列降级。legacy清单只接受可核验既有记录，不允许新CHG自行填legacy。无需业务数据迁移或新运行依赖。
