## 1. 用户要求与当前调用链

用户希望Goal计划生成后先出现在面板供查看，批准后才执行；不应等待执行开始才显示计划。沿用此前要求：AI Office业务代码保持原版，确认菜单继续使用执行／修改／取消。

只读源码核对：GoalContext::update的非执行编辑分支提交set_plan并queue_review后直接返回，缺少即时project；执行分支末尾已有project，runtime回合收尾也会project_goal。固定审核在goal/review.rs调用review_displayed后直接等待真实问题答案，在此等待期间尚未结束回合，因此初始计划可能尚未推送面板。这是静态调用链发现，尚未以新回归运行证明，不冒称已经修复。

office.rs现有投影支持draft→queued及三项steps，原版WhiteboardProgress仅running时按时间增长；可复用。执行中replan仍可能保留active阶段，但confirmed_version落后于plan_version，必须以当前版本是否批准修正展示，不能只看phase。

方案符合根ADR-0001的先展示、后确认执行边界；不改变确认本身或授权语义。

## 2. 预期行为

1. 完整初始计划生成并进入原审核流程后，在等待答案期间就将当前目标、任务和计划版本推送到原面板。白板沿用前三项上限，完整任务在现有任务列表及聊天计划可查。
2. 新版本未批准时，面板明显写明“计划待批准”；初始任务进度0，白板queued，不启动执行时间动画，不派工、不产生业务交付。展示不等于批准。
3. 用户选择执行且答案可靠保存后，立即推送批准后的状态，再沿原回合剩余预算继续。修改、自定义要求、取消、超时、停止及重启不会被当成执行许可；结果按原规则保存及展示。
4. 用户修改或执行中重规划产生新版本时，新计划再次在面板等批准；保留有效已验收事实和原有人工阻塞。已验收项不为展示而清零，待批准期间停止该板时间增长。
5. 保留原版布局、菜单、三行上限、整体验收后统一100%的现有前端规则。不新增面板批准按钮或独立用户消息气泡。
6. Office推送沿既有尽力队列；展示失败不能代替确认、授予权限或改变AgentLoop结果。测试检查实际等待期间快照最终可见，不把异步入队冒称浏览器已渲染的可靠确认。
