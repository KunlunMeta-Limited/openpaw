# CHG-2026-0007：审批生命周期闭合

## 先说结论

本变更确保回合重置或取消清理待审批请求时也发送 `permission.replied`，客户端可按 `requestID` 关闭失效权限卡片。它不新增路由、不修改人工批准和拒绝的原有字段，也不把取消当成人工审批。实现和历史测试已有记录，但正式 PR、CODEOWNER 审核与本次复测仍缺失。

## 2. 变更原因

旧流程在 `begin_turn` 或 `abort_all` 清除 pending permission 后，客户端可能只收到 `permission.asked` 而没有结束事件。轮询能看到空列表，但事件驱动客户端会保留已经失效的权限卡片，造成错误授权入口和状态泄漏。清理动作必须在线性化消费 pending 的同时发送对应结束事件。

## 9. 影响、数据流和实现

### 影响分析

事件客户端会多收到用于关闭失效请求的结束事件；轮询客户端行为不变。`reply`、`begin_turn` 和 `abort_all` 在同一生命周期锁内竞争，至多一个操作消费请求。权限模型不放宽，取消和重置只能拒绝请求。事件发布到 session 和全局通道，日志不得包含工具敏感参数。

### 数据流和失败路径

```text
permission.asked -> pending
  -> 人工 reply    -> permission.replied(approved/rejected) -> 删除 pending
  -> begin_turn    -> permission.replied(rejected/reset)    -> 删除 pending
  -> abort_all     -> permission.replied(rejected/cancel)   -> 删除 pending并唤醒等待者
```

重复 reply 或已清理 ID 仍按既有接口返回不存在；不得产生第二个结束事件。

### 实现方案和选择理由

结束事件由拥有 pending 的 `HostApprovalManager` 生成，避免 HTTP、runtime 和事件层分别猜测生命周期。替代方案是客户端仅靠轮询消除卡片，但这会保留明显延迟和竞态，因此没有采用。
