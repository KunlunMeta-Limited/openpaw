# CHG-2026-0026：图片与音频附件理解

状态：已批准（approved），2026-10-13。用户在审阅最终方案后明确回复“开始实施”，授权按 Q1–Q17 和第 4.1 节范围分两阶段实施。

用户在 feature/multimodal-support 分支调用 grill-with-docs，询问 OpenPaw 能否支持图片甚至音频。
本文件按轮次记录事实、已确认决定和待决项。历史 CHG 的批准不作为本变更的实施授权。

## 1. 基线、问题与目标

- 工作目录：wt-merge；设计和实施分支：feature/multimodal-support；当前交付分支：feature/add-multimodal-capabilities。
- 起点：merge/openpaw-engine_host 的 7c8262ee84eb77508a2da200714408e5f3aa5ebe，与 GitHub 同步。
- 现状：核心消息已有 Image，但音频没有专门内容类型；Host 输入和部分 Provider 转换仍以文本为主。
- 目标：用户提供图片或录音附件，模型理解其内容并用文字回答；CLI 与 Host 共用输入、模型调用和会话历史能力。
- 图片生成、语音回复、实时通话不属于目前已确认的首版目标。

## 3. 事实核查与资料

以下为实施前的代码证据；位置和“当前”均指 7c8262e 基线，实施清单见第 4.1 节：

| 路径与位置 | 当前行为与影响 |
| --- | --- |
| crates/openpaw-core/src/message.rs:137–143 | Image 有必填 url、可选 media_type / data；没有类型化媒体来源或验证，尚无 Audio |
| crates/openpaw-cli/src/chat.rs:142 | 用户输入通过 user_text 创建，尚无附件入口 |
| crates/openpaw-engine-host/src/protocol.rs:335,374,390；src/http.rs:427,512 | Host 只拼接 text part，图片输入被忽略 |
| crates/openpaw-llm/src/openai.rs:73–74 | 仅转换 Text / ToolResult 等既有文本内容；Image 被跳过；使用 Chat Completions |
| crates/openpaw-llm/src/anthropic.rs:64–70 | 直接序列化 Core 内容；现有 Image 字段没有转换成 Anthropic 所需 source 对象 |
| crates/openpaw-store/src/session.rs:100–107,155–162 | Message 原样 serde 入 JSONL；内联媒体可随消息保存，但没有独立附件资源仓 |
| crates/openpaw-engine/src/compaction.rs:46–50,188–189 | Base64 长度进入 token 粗估，摘要输入只看图片 URL；压缩后附件语义可能丢失 |
| crates/openpaw-engine-host/src/message_projection.rs:159–166 | REST 历史投影跳过 Image / Document |
| crates/openpaw-core/src/provider.rs:348–356；crates/openpaw-llm/src/config.rs:39–48 | 能力与配置均没有逐模型图片/音频输入声明 |
| crates/openpaw-engine-host/src/protocol.rs:475 | /provider 的模型仅有 id/name；connected 不能证明模型的媒体能力 |

现有 Fork / Revert 处理消息前缀；Q6 已选择原件随消息内联保存，Q9 已选择压缩后按编号回看。
当前不能把“有 Image 枚举”和“能原样落盘”视为已实现端到端图片理解。

压缩接入补充事实（静态核查，未运行故障复现）：

- AgentLoop 默认 compact_options=None；生产 CLI / Host 未调用 with_compact_options。
- CLI chat.rs:204–208 用执行前索引提取生成消息；Host runtime.rs:2459,2535 的 UUID 分配和提交
  也依赖执行前索引。压缩会缩短、改写模型上下文，这种提取方式不能作为压缩后完整产出的依据。
- turn_execution.rs:53–58 当前只返回 StopReason 和 checkpoint；AgentEvent 不含完整助手消息和工具输入。
- 同回合先生成后压缩的消息尚未落盘，不能从旧 JSONL 或结束时 UUID 差集重建。
- Store 保留原消息事实。媒体查找可基于有效历史；模型压缩视图与公共会话记录必须分别处理。

补充的实际客户端事实（只读，未修改其仓库）：

- OpenWork：../openwork-ui/apps/app/src/react-app/domains/session/sync/attachment-file-part.ts:184–188,331–337
  将图片作为 type=file / mime / filename / data URL 交给 Host；audio 当前不作为模型 file part 发送，
  主要留下工作区路径提示。不能将 OpenPaw 支持音频理解等同于 OpenWork 已有录音/音频直传界面。
- AI Office：../ai-office/src/services/officeGatewayApi.ts:156–160 目前只发送 text parts。
- Tools read_file 使用 read_to_string；ToolCallOutcome 和 ToolResult 均以 String 为主内容。
  要支持 Agent 读取媒体，需扩展富工具结果，并沿用输入验证、工作区规范化、guardrail、manual 审批和取消链。
- Tools 和 Host 已有 Base64 依赖；UUID 已在 Core / Store 使用。当前没有现成的媒体格式/尺寸/时长解析器。
  不为生成音频或转码引入解码器；若实施需要其他依赖，必须登记具体包、用途和默认依赖树影响。

官方 OpenAI 文档，2026-10-13 实际获取：

- [Audio in Chat Completions](https://developers.openai.com/api/docs/guides/audio-chat-completions)：
  原生音频对话模式使用具备音频能力的 Chat Completions 模型；Responses 文档当前描述文本/图片输入及文本输出。
- [GPT Audio 1.5](https://developers.openai.com/api/docs/models/gpt-audio-1.5)：
  模型列出 Chat Completions 支持、Responses 不支持；不能从“音频模型”推断它也支持图片。
- [Chat API reference](https://developers.openai.com/api/reference/resources/chat)：
  input_audio 使用 Base64 data 与 format，当前列出的输入格式为 wav / mp3。
- [Images and vision](https://developers.openai.com/api/docs/guides/images-vision)：
  Chat Completions 与 Responses 均支持视觉模型的图片理解，但图片内容块的结构不同。
- [Speech to text](https://developers.openai.com/api/docs/guides/speech-to-text)、
  [Text to speech](https://developers.openai.com/api/docs/guides/text-to-speech)、
  [Realtime API](https://developers.openai.com/api/docs/guides/realtime)：分别定义转写、语音合成和实时交互。

音频输入并不要求生成音频输出；本轮确认文字回答，不把音频输出解码纳入隐含需求。
模型的输入能力分别确认，不能因某模型能听录音就假设它能理解图片。

补充协议资料，2026-10-13 实际获取：

- [Chat reference](https://developers.openai.com/api/reference/resources/chat)：tool 消息只允许文本，
  需要 role=tool 与 tool_call_id；媒体放入随后 user 输入是应用适配选择，尚无通用服务兼容保证。
- [Function calling](https://developers.openai.com/api/docs/guides/function-calling)：Responses 有图片/文件
  工具结果路径，但 Q4 未将新增 Responses 纳入首批范围。
- [Anthropic Vision](https://platform.claude.com/docs/en/build-with-claude/vision)：图片 source 支持
  Base64 / URL / file_id；JPEG/PNG/GIF/WebP，动画只首帧。本轮输入来源按 Q10 限定为本地或内联。
- [Anthropic Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)：
  tool_result.content 可含文字和 image.source，图片工具结果可用原生结构编码。

格式、编码后的请求体、图片像素尺寸及历史中累计附件数量均需按所选上游检查。
应用单附件上限不是某个模型的完整限制；Base64 体积与原件体积也不能混用。

“音频只能用 Chat Completions”必须限定到这类原生 HTTP 对话与具体模型。
转写 API、语音合成 API、Realtime 是独立路线；第三方的 OpenAI-compatible 声明不保证图片或音频能力。

## 6. 实施设计、接口与替代方案

实现为入口适配 → 中立内容块 → 现有共享执行 → Provider 协议适配 → 共享历史保存/投影。
Host、CLI 和 Provider 不各自维护另一套媒体会话事实。Q6 已选择在会话记录中保存附件原件；
重启与会话分支沿用内联数据，模型上下文压缩后按 Q9 保留编号并通过工具按需读取原件。

已确认的路线及其取舍：

- Q3 已选原生音频，可保留声音层面的信息，但要求模型具备相应能力；先转写更容易接入文本模型，
  对语气、说话人和非语言声音的保留有不同语义，本轮不把它作为隐式替代。
- Q4 已选扩展既有 Chat Completions / Anthropic 适配器；新增 Responses / Realtime
  会引入额外请求、事件与会话合同，另行规划。
- Q6 已选媒体内联，JSONL 自包含且可沿用消息复制；相比独立附件仓，记录和分支文件更大。
  不将该选项解释为允许把 Base64 当作文本发送、按其字符数估算模型 token，或无限制地接收附件。
- Q7 已选显式模型能力；Q8 已选媒体工具输入。工具结果仍需保留原调用 ID 和文字结果，
  Provider 分别映射媒体内容；Q11 已选 Chat 的附加媒体输入适配，Anthropic 使用原生工具媒体内容。

共享职责按已确认方向收敛：Core 定义中立媒体/能力类型，LLM 负责协议编码与模型能力检查，
Tools 负责有权限的文件读取，Store 负责有效会话记录与附件查找，Engine 传递富工具结果并维护压缩语义，
CLI / Host 负责各自的输入及输出投影。共享实现不依赖终端或 HTTP。

压缩后的附件查找必须基于当前会话可见历史，而不是直接扫描原始 JSONL 绕过 staged / committed revert。
Fork 只保留选定前缀可访问的附件；压缩后的 Fork / 重启仍须恢复被摘要引用的原件。
压缩只改变模型上下文，不授予跨会话任意附件读取，也不把 Base64 注入摘要文本或全文搜索索引。

API 路由/字段、CLI 参数、核心公共 Rust 接口及依赖见以下已批准条目。
Office 动作不携带附件内容；既有失败隔离、取消、权限及默认 CLI 无 Axum 的约束继续适用。

### 6.1 中立内容和工具合同（提案）

- 新增 InlineMedia：id（稳定附件编号）、mime（规范 MIME）、data（原件 Base64）、filename（可选名称）。
  UUID 复用已有依赖。字节长度从有界解码结果取得，不信任客户端自报大小。
- 保留 Image 的 url / media_type / data 旧读取形式，新增可选 id / filename；新写入采用内联数据，
  不依赖原始本地路径。Audio 保存相同身份/名称及规范 MIME / Base64 原件。
- ToolCallOutcome 与 ContentBlock::ToolResult 增加默认空的 media 列表，保留 content:String、
  is_error、tool_use_id 及既有其他字段。文本旧构造器继续可用，非媒体结果保持原线格式。
- read_file 识别已支持的图片/音频，返回文字说明及媒体；未知二进制仍给错误，文本读取语义不变。
  read_attachment 接受 {attachmentID}，只读当前会话可见附件和本回合可访问缓存。
- 用户主动 --attach / /attach 是对该明确文件的输入选择；Agent 自动读取仍受工作区边界、
  验证、manual 审批与取消控制。历史附件读取同样不绕过护栏。
- AfterToolCall 的结果替换按完整结果处理：省略 media 的 Replace 视为无媒体，error 不携带媒体；
  显式保留/替换的媒体重新校验，避免文本 Hook 改写后原件仍无提示地进入模型。

### 6.2 输入、展示与错误合同（提案）

- CLI --attach 可重复；/attach 后余下文本作为一个文件路径，支持带空格路径；待发送附件按添加顺序。
  /send 发送纯附件，/clear-attachments 清空待发送列表。命令不作为模型消息；空列表 /send 本地提示。
  --attach 进入同一待发送列表，不隐式产生多个回合；EOF 不默默发送未确认的待发送输入。
- Host 保留既有 /session/:id/message 与 /prompt_async 路由；file part 为
  {type:"file",mime,filename?,url:"data:<mime>;base64,<原件>"}。允许纯附件，保留 parts 的文字/媒体顺序。
- 仅 text 的旧请求维持原拼接规则及直接 text 优先。直接 text 加 file parts 时以 text 为首个文字块，
  后接文件原有顺序；parts 中文字不再次重复。非媒体的既有兼容 part 不改变既有忽略规则。
- 首版远程 URL / file:// 不自动加载。声明的图片/音频 file part 无效或不支持时明确拒绝，不能静默丢弃。
- REST / SSE 用户媒体采用公开 file part；工具媒体使用关联 callID 的工具 attachments。
  可以返回客户端本身要展示的 data URL，但错误、日志、Office 动作、终端摘要及 FTS 不含 Base64。
- 单图 5 MiB、单音频 20 MiB，输入回合最多 4 个且总计 20 MiB，均按原件字节计算。
  新媒体工具读取也须经过本回合预算；原件回看不授予无限制模型请求。实际发送另检查累计内容、
  序列化请求字节及所选 Provider / 模型更严格限制。
- Host 消息路由允许 Base64 膨胀后的有界 body（提案 32 MiB）；其他路由沿用原上限。
  文件不存在、Base64 / MIME / 内容头无效、不支持模态返回确定的 400；超限为 413；
  这些拒绝发生在接收回合和写入新消息之前。同键不同媒体/顺序为既有 409 幂等冲突。
- 指纹包括规范化文字、媒体 MIME / 原件身份 / 顺序、有效 provider / model；不包括每次重试新生成的
  服务端 UUID。请求被接受后附件编号固定，重放不重复生成输入、附件或回合。
- 文本说明与附件不匹配、模型不支持混合输入时明确失败，不自动换模型、不转写替代。

### 6.3 模型配置与 Provider 编码（提案）

环境变量提案 OPENPAW_MODEL_CAPABILITIES，值为按协议和模型键索引的 JSON，例如：

```json
{
  "openai": {
    "vision-model": {"input": ["text", "image"], "context_window": 128000},
    "audio-model": {"input": ["text", "audio"], "context_window": 128000}
  },
  "anthropic": {
    "vision-model": {"input": ["text", "image"], "context_window": 200000}
  }
}
```

示例模型名是占位符，不代替用户选择，也不声称该配置验证了某服务的能力。
context_window 为可选正数，未给时沿用现有估计；不从模型名或 API key 推断媒体支持。
配置绑定当前服务地址的运行快照，变更服务时必须重新确认声明，客户端请求不能授予服务能力。

- 输入 text 默认可用；未知模型 image / audio 默认 false。CLI model list、config / doctor
  与 Host /provider 共用解析结果；配置错误脱敏且在请求模型前失败。
- Capabilities 增加 image_input / audio_input；LlmProvider 增加有默认实现的逐模型能力查询，
  现有 capabilities 方法保持可调用。实际请求必须按有效模型检查，不能用默认模型能力替代覆盖模型。
- Host 模型目录新增 capabilities.input={text,image,audio} 的明确布尔值，保持 id / name 与既有 connected 含义。
- Chat 图片为 content[] 中 image_url:{url:"data:..."}；音频为 input_audio:{data,format:"wav"|"mp3"}。
  输出保持文字，不开启音频生成；沿用文本 SSE 的终止、工具调用和错误处理。
- Chat 工具先返回全部配对的文本 tool 结果，再生成注明来源的媒体输入。它只存在于请求编码，
  不能落盘成用户提交、触发新回合或影响 Fork / Revert 的用户边界。
- Anthropic 显式映射已有内容和 image.source；工具图放在 tool_result.content 数组，维持 tool_use_id。
  Document / Unknown 不作为本轮新能力，旧内容保留但不误称图片或音频可用。

### 6.4 历史、压缩和完整产出（提案；Q17 已确认启用）

- 原件只作为会话内容内联保存，不引入旁路附件文件仓。已提交原件从有效 Transcript 建立查找快照；
  本回合未提交工具媒体进入会话范围临时缓存，失败/取消/清理后不泄漏到另一回合或会话。
- 附件编号在同一原件续问中稳定；Fork 携带选定前缀原件及编号，但读取绑定分支会话自己的记录。
  staged revert 隐藏的媒体不可读，unrevert 可恢复；committed revert 后隐藏原件不再被新回合查找。
- 摘要对每个被压缩附件确定性保留 ID、MIME、名称和来源简述；该清单不靠摘要模型自发记忆。
  不把 Base64 发给纯文本摘要模型。语义说明可复用已有回答，不声称文件名能代替实际内容理解。
- 磁盘公共会话记录保存真实输入、完整助手与工具结果；摘要和 CompactBoundary 属于模型上下文，
  不伪造新的用户输入或改变外部 message / turn 身份。重启从有效历史恢复，必要时重新建立压缩视图。
  本轮不新增另一份独立持久化模型上下文事实源；因此长会话重启可能重新请求摘要。
- Engine 在消息实际生成时收集完整本轮产出，TurnExecution 返回 generated_messages 与原 checkpoint。
  不从压缩后 Session 的旧索引或 UUID 差集倒推。原 AgentLoop 入口保留兼容包装；收集器不依赖 Host。
- Host 按完整产出次序分配既有 msg_<session>_<turn>_* ID，保留事件与持久消息对应；CLI 和 Host
  都委托 Store 提交完整结果，不把只展示文本或被压缩的结果当作已保存。
- Q17 已同意启用自动压缩，两端共用触发设置；模型输入能力、上下文窗口、工具 schema、生成预算和
  媒体请求预算纳入触发。优先压缩旧内容，保留当前输入及工具配对，不能以压缩丢弃刚发送的附件。
  无法压缩到合法预算时给出确定错误，不循环摘要或悄悄删除当前内容。
- 媒体 token 估算按类型和可用模型规则计算，与实际计费区分；原件/请求体字节单独精确约束，
  不再使用 Base64 长度除以 4 作为真实媒体 token。真实模型误差由后续实测记录。
- 取消、执行错误/panic、future drop 和提交失败保留已接收输入，恢复完整 Session 与临时媒体状态；
  工具外部副作用仍不回滚。提交成功之后才发布既有完成/idle 终态。

### 6.5 阶段与替代方案

阶段一：共享内联图片、能力配置、完整富工具结果、CLI / Host 输入与历史投影、read_file / read_attachment、
历史续问与压缩接入（按 Q17），完成图片的两种协议契约。阶段二复用以上结构接入 WAV / MP3 原生音频，
补音频媒体读取、Chat 请求和相同历史矩阵；不增加转写、语音合成、Realtime 或第三方前端改动。

替代方案及取舍：受管附件文件仓已在 Q6 被内联方案替代；转写在 Q3 另行规划；Responses / Realtime
在 Q4 另行规划；自动选模型在 Q7 被显式能力拒绝替代；全量媒体持续留在上下文在 Q9 被按需回看替代。
完整生成收集比执行后索引切片多一份中立执行记录，但能处理同回合压缩和完整工具消息，是可靠提交所需。

### 6.6 继续保护的边界

最终批准清单以外的业务路径不修改；Core 不引入 Host / Office / HTTP 类型，Engine 不新增 Store 依赖。
不修改 CI、xtask 计数/门禁、现有预算、审批策略、Office 动作语义、跨进程写入保证或网络 Provider 回退策略。
不修改 OpenWork / AI Office 源码和测试，不处理用户真实会话，不编辑凭据、环境文件或部署配置。
若实际媒体解析需要新增 workspace 之外的依赖、未列文件或预算调整，先补具体必要性与影响，再按已有授权核对。
Core 的 Base64 依赖边明确登记，不新增转码/语音处理库。

## 7. 验收与回滚

本轮实现按以下要求验证：

- 纯文本旧会话仍可读取和使用；旧请求保持兼容。
- CLI / Host 的文字与附件顺序、模型请求及历史可用性一致，附件不会被静默丢弃。
- Provider 编码符合各自协议，不支持能力时给出确定错误。
- 重启、会话分支、回退/取消回退和多次模型请求后的附件语义正确。
- 无效、超限、缺失附件以及取消/模型失败/保存失败遵循确认后的行为。
- 使用隔离图片/音频字节样例验证编解码、路径、历史及完整请求；Q16 已明确真实模型稍后验证，
  不将模拟文字回答称作图片/音频的实际理解，也不将本地桥接成功称为某第三方服务已验证兼容。
