## 3. 实现与数据流

### 3.1 组装顺序

仅在 session_tool_host 共用入口中，将现有 ContextToolHost 包装移动到原工具与 GoalToolHost 之间：

`既有工具 → ContextToolHost →（主会话）GoalToolHost → QuestionToolHost`

主会话的原件读取从 Goal 现有 allowed／observe 入口经过，保留真实 ToolInvocationContext；子会话仍不安装 Goal 包装。QuestionToolHost 的位置与生命周期不变；既有原件 reader、权限、取消及分页实现保持，不另建客户端、writer 或调用链。创建／恢复／fork 继续复用同一组装入口。

### 3.2 可用验收观察

Goal 的既有文件／检查工具规则保持。对 read_context_record，仅将实际成功返回的合法分页结果作为读取观察；原件错误状态也必须被检查，避免外层调用成功却把失败原件标成有效读取。记录实际输入引用及分页，既有 task_id／turn_id／plan_version 归属与原件来源检查不放宽。页范围与语义是否足以支持某条条件仍由主 Agent 核对，与既有 read_file 的职责一致。

wait_agent／get_agent_status 继续记录协作事实，但不因 is_error=false 或 status=completed 无条件成为业务验收观察；排队、运行中、超时、失败、取消或仅有状态不能直接通过全部条件。不为本修复更改委派结果格式或领取一次的语义。

### 3.3 接口与兼容

不新增公共 Rust 类型、trait、函数或字段，不修改 GoalRuntime 五项同步效果。不增加工具、HTTP 路由、SSE 字段、JSONL 格式或依赖。现有 Observation 形状不变：新增的是对实际 read_context_record 调用的正确记录，不补造旧观察或重写历史 verification。旧数据继续可读；旧会话仅由用户明确继续后沿实际读取流程复核。
