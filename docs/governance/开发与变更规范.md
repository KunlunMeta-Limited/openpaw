# 开发与变更规范

适用OpenPaw；Office另受Rx预审批。用户当前明确指令优先于参考资料，参考framework和旧master-plan不是独立授权。

一Tx一主CHG，采用参考框架十二节中文表格作为单一事实源。所有功能、bug、文档、工程变更都登记；阶段完成后普通CHG不再受Tx串行限制。实施授权可引用明确用户指令，PR批准必须由非作者针对当前提交作出。工具不提供approve命令，不把姓名/时间非空当身份认证。

CHG新格式为openpaw/chg-review-v2，保留十二节中文Markdown作为单一事实源。第一页独立登记提案版本、方案审核人/时间/证据/批准对象、开发与验证、交付验收、平台PR、实际合入。编码前先形成可审核方案，用户批准具体版本后实施；方案批准不要求尚未创建的PR URL。review只表示待审，不作为编码授权。工具核对版本与事实结构，不认证聊天身份或自行填批准。

每个文件写明现状/为什么需改、具体模块和方法、复用/延展/修改/新增判定、影响和可验证完成标准；条件文件写明触发条件。不要求重复总背景或复述每行代码，无变化章节可短写并给理由。审批人应能据此判断目标、必要性、范围和风险；不能用“必改/有必要”代替理由。

实施前固化方案版本（优先使用已提交的CHG对象），登记用户实际决定；方案正文第2—11节、介绍和关键计划字段绑定该对象，元数据登记不推翻原批准。增加文件、方法实质变化、协议/权限/数据/依赖/验收变化先修订同一CHG并重新审核，控制台列新旧差异，不另起一个Tx或审核总单。批准范围内私有细节可迭代。

开发提交可按完整逻辑适度整合，优先中文信息。完成后运行规定全量及原生双平台验证，提交准确交付版本和证据给用户验收；用户验收后才能创建PR。交付验收不是平台Approve。PR创建/审核/合入分别补登真实URL、head、当前提交Review和merge SHA，前序状态在下一任务开始前同步。关闭但未合入不算closed；登记合入事实无需让已合入提交预先记录自身SHA。

一Tx一主CHG是初期默认。仅经用户明确批准可在一个主CHG中用“关联修订=CHG编号@准确版本”共同交付（本次T3与0001），关联项各自批准、验证及验收；不能通过简单合并文件表夹带未审改动。重叠文件每行填写共同修改职责并引用另一CHG，取更严格保护。历史“元数据维护”和用户授权的“说明扩充”分别列准确CHG路径；前者只补首页事实和追加履历，后者可扩原因/方法/完成标准，不改原文件/操作/必要性、保护、测试及历史正文。历史CHG禁止删除/重命名。旧记录仅通过profile固定的准确路径/历史提交兼容，不补造事前批准，不成为新代码免审通道。


允许文件必须具体到仓库内路径，不用全仓通配。每项“必改/条件”分开；实际diff不得超出允许集合，必改必须出现，条件未使用说明原因。重命名登记旧/新两端，删除登记原因并处理引用。保护等级不得低于profile，L4要求critical风险声明；门禁自身和依赖/权限/协议变更不能自行降级。

代码改动优先复用；新增必须解释不可复用的职责。bug先复现，独立D记录/回归；相关修复可按完整逻辑整合提交，提交信息优先中文；不改断言掩盖失败。私有实现可在授权边界内迭代，扩大API、权限、依赖、持久化或Office范围须补方案和授权。

文档影响表列具体文件、章节和理由。行为→需求/使用说明；职责/状态→设计；路由/事件→契约/fixtures；存储→迁移恢复；权限→风险回归；依赖/平台→兼容/构建/CI。不涉及也写理由。自动检查只核对关联和结构，语义由人工评审，不以更新时间或任意改一行证明同步。

Office任何修改先Rx：现状/复现或必要性、无修改替代、方案/准确范围、功能/协议/数据/权限/部署/双平台影响、测试/回退、批准版本与证据。用户批准总计划、允许提案、发现bug、CI绿灯都不能替代Rx批准。只读核查和仓库外测试副本不改Office源工作区。

历史ADR已按用户指令还原。历史报告保留事实，不批量重写；无关m2/m5格式改动保留工作区，提交只选择本CHG文件。DCO使用git commit -s，不自动合入、不强推。平台required checks/CODEOWNERS需真实账号和人工配置；本地文件无法保证这些设置已生效。

## 初期里程碑与PR前置核查

master第14节维护M0—M8台账和逐项里程碑章节，第10节Tx“执行导航”链接实施方案，第14.2节逐项对照固定Office文档/Schema、master章节、产物和验收。开发前读取本Tx导航，实施中更新主CHG定位；不得只链接整个master代替具体条款。

创建PR（包括Draft）前，按14.3逐项检查本Tx必需产物、协议、复用/范围、文档、全量及原生双平台证据；失败/缺失/未批准必需Rx标阻塞，满足后才能创建。先push已授权开发分支以复用原CI的Linux/Windows矩阵，治理基线取与集成分支的merge-base，不只检查最后一次提交。PR与分支push可能各有一轮CI，使用准确SHA和run区分，不能把两轮都计为产品覆盖增加。已有T0 #4继续Draft修订，不新建替代PR抹掉历史。

技术核查由开发者/agent记录，通过后还需用户对准确交付版本验收，再提PR；不代替非作者人工PR审核。批准待合入仍非完成；实际全部必要PR获批合入后按14.4更新master台账、主CHG/验证履历与交接。记录实际审核证据/批准提交/合入SHA/日期，旧失败保留，关闭未合入不算完成。完成登记可在下一Tx开工文档同步真实前序事实，不无限要求一个已合入PR记录自己的合入SHA。

这些是人工/agent必须遵守的工程规则，现有自动工具只核查已实现的结构/范围/证据，不能认证人审身份或自动判定真实产品达标；本次不声称新增了自动里程碑判定器。初期结束后按CHG正常PR，取消Tx串行；协议追踪/测试/真实状态/Rx规则继续有效。
