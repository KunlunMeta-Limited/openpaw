# 单对话持续协作与媒体工具

本能力属于Host的通用持续任务协调，不包含文章选题、审稿等业务流程。当前r16候选在验证中，不能据此宣称已切换生产服务或完成全部验收。Office工程不改；不同对话仍各有独立Run，本文只讨论一个对话。

## 为什么一轮回复之后还可以继续

普通Agent收到模型的最终回复就结束该轮，这是正常行为。持续模式把“一个阶段结束”和“用户整个目标停止”分开：同一个主Run、Session及取消信号，在阶段结束后根据真实检查点再次调用原AgentLoop。子Agent每个有限任务仍正常结束，之后可重新接受工作；不同角色可并发，同一角色排队，依赖前序结果的复核应等待结果。

只在可信配置开启且用户明确要求持续时，主Agent调用`continuous_task start`。普通问答保持原行为。`checkpoint`保存成果摘要、下一步；用户要求直到停止时不得自行`finish`；有明确有限完成条件时在start登记，满足后可finish。模型对“条件已经满足”的判断仍需业务验收，不把声明当成事实核验。

## 配置与启动

在原Host TOML合并以下字段，原home、roots、slots、Office配置不变。完整字段示例见[host-config.example.toml](host-config.example.toml)。不自动修改用户已有配置。

```toml
max_active_runs = 6
run_timeout_secs = 0
# 保留原有工具；下面展示本示例所需集合。
tools = ["read_file", "glob", "grep", "web_search", "web_fetch", "write_file", "edit_file", "render_visual", "generate_image"]

[agents]
enabled = true
max_active_children = 5
max_delegations = 0
max_model_requests = 0
max_output_tokens = 0

[agents.continuous]
enabled = true
output_dir = "outputs"
auto_approve = true
stage_pause_ms = 250
max_open_items = 2
```

默认配置仍关闭持续模式、最多两子Agent。零表示不设总时限或累计配额，实际请求仍受模型单次输出、网络空闲、工具超时和机器资源限制，不代表无费用或服务不会失败。五子并发需要至少六个空闲全局运行槽；其他会话仍共享原全局容量。

启动沿用原入口：`openpaw engine-host --config /绝对路径/host.toml --env-file /绝对路径/models.env --port 0`。日常启停/编译仍用`scripts/openpaw-office.sh`及相应配置变量。本文不改变其默认配置路径。

## 自动授权的范围

持续任务已start之后，原白名单内的文件写入/编辑、图片与图表，只在`outputs`真实子目录下自动批准。原精确输入审批记录、一次消费、独占资源锁及锁后路径/文件前置条件复验全部保留，并在host_events记录来源。目录外仍需人工审批。shell、删除、部署等不自动批准。停止后不再产生新的自动授权；已经提交的文件不回滚删除。

默认子Agent也可以使用Host已开放的这些产物工具；显式`agents.tools`角色白名单仍能进一步缩小权限。不要把输出目录设成整个工作区。

## 生图与图表

`render_visual`无需图片服务：`kind=diagram`使用nodes/edges绘制SVG流程图；`kind=bar_chart`使用非负data及source绘制柱状图。文字转义，不接受任意脚本或远程SVG。数据来源由调用方提供，工具不会把来源标签冒充事实复核。

`generate_image`调用可信配置的OpenAI兼容图片API，保存实际PNG/JPEG/WebP；服务必须支持base64结果。配置与聊天模型分开：

```toml
[agents.images]
base_url = "https://你的图片服务/v1"
model = "你的图片模型"
api_key_env = "OPENPAW_IMAGE_API_KEY"
```

在同一个OpenPaw正式模型`.env`中加入`OPENPAW_IMAGE_API_KEY=你的图片服务密钥`。CLI通过原ModelEnvironment只读加载，不复制进项目、不导出到工具进程；系统环境优先，显式空值拒绝。不能把DeepSeek聊天凭据当作另一个服务的图片凭据。只配置images而没有独立密钥时启动明确失败，避免运行中才发现配错。

工具请求`POST {base_url}/images/generations`，发送model、prompt、n=1、size；默认不发送response_format，不按模型名猜字段支持。服务明确要求时可在images中设置`response_format = "b64_json"`；不跟随重定向。限制响应/文件大小，检查格式结构及扩展名，失败或取消不提交文件。此结构检查不是完整图片解码或视觉语义审核。服务只返回URL、图片超限、格式错误等会明确失败；不生成占位图。照片/插画的视觉关联、真实性需要可用视觉模型或人工审核，本轮不假装已经自动完成。

## 一次输入示例

下面是四事项、双作者、约1000字的完整演示提示词。文章编号、字数、作者安排、评分和退修规则只在提示词中，不进入通用引擎。配置须已启用持续模式且`max_open_items=4`；实际工具以当前角色白名单为准。复制下方全文：

```text
完成技术文章的持续生成与交付。

在当前单一对话中持续组织团队工作，直到我明确要求停止或点击停止。只输入这一次；不要每篇询问是否继续，不要把阶段最终回复当整个目标结束。先调用 continuous_task start，不设置有限结束条件，不自行 finish。

王明负责调度和最终验收；周理（organize）选题、摘要、提纲与有限来源核对；陈书（draft）、刘市（review）都是作者，每次各自负责一篇；李研（research）配图、图文合稿；赵审（audit）审核实际合稿。role_id决定真实人物，title、instructions、context内的称呼必须与它一致，不能把给刘市的工作派给draft。非当前角色的姓名只用来明确成果交接对象。

最多同时开放4篇未验收文章，每篇只建立一个稳定work_item。先open_item，再委派，验收交付后close_item；新编号从实际输出目录中未占用的编号开始，不覆盖已有文章。各篇在outputs/article-workshop/编号/内保存outline.md、article.md、图片及review.md，所有人使用同一准确目录。选题围绕AI Agent、多智能体和AI工程实践，避免与已存文章重复，不为追热点无限搜索。

每篇正文约1000字，900—1200字可接受；这是近似要求，不按每节精确计数、不无限压缩重写、不为了估字数新增工具请求。标题、摘要、正文要一致，章节逐步展开，具体论点应有例子及必要来源；不虚构实时信息和实测数字。来源核对有界，无法核实就明确标注，非核心条目不应阻塞其他文章。子任务最终回复只交付结论、问题、准确文件路径，尽量不复述整篇正文。

队列与调度：按工具回执task_id、role_id、title、work_item建立任务表，区分排队、在途、执行结束、业务验收及不合格。accepted不是完成，completed也不等于文章验收通过。优先给空闲作者独立文章；同人待办进入FIFO，不重复提交仍在途或已成功完成的同一工作。使用wait_for_completion=false交付有限任务，处理不同文章的独立阶段；没别的可派工作时用delegation_status等待，下一次只等待pending_task_ids，已经收取的终态从等待集合移除。收到一个结果就及时核对并衔接，不等四篇全部结束，也不为动画添加空任务。

真实成果交接：前序任务成功后，以实际返回的task_id填写source_task_id，同篇work_item保持一致。周理提纲→实际作者；作者正文→李研；李研图文合稿→赵审；赵审退修→实际负责该问题的作者或李研。context传真实产物路径、必要摘录及本轮修改要求，不传不存在的成果、不串其他文章。每次任务绑定明确对象和版本：第几篇、哪份文件、首次还是第几轮退修。最近的动画不等于人物当前真实执行任务，以任务表和回执为准。

写入能力：派工前检查每个角色available_tools。有edit_file可做精确局部替换；只有write_file时，可以先读取实际全文，再对这篇约1000字的文件做有界整文件保存并回读，保留已有图片链接和来源，仍经过Host原审批。不要给只有write_file的角色同时下达“必须edit_file、禁止整文件保存”的冲突要求。没有写工具则不能派落盘任务，应由有相应工具的同事执行。若只返回修改建议而未保存，不能报文章已修完。

配图合稿：李研读取真实正文后，生成2—3张与论点有关的图片或SVG图表；每张必须有图片标题、图注及来源/自绘示意说明，相对链接实际写入同一个article.md，不能仅在旁边存图。工具不支持真实生图就使用真实SVG并说明示意，不伪造照片和视觉验收。检查图中文字与正文一致、无明显越界或遮挡；没有渲染能力须如实说明限制，不把读SVG源码冒充看过渲染结果。

审核与退修：赵审实际读取article.md和图片，核对主题兑现、结构递进、工程深度、证据质量、自然表达、图文关联、图片准确性与创意并评分，保存简明review.md。必须修复的问题写明准确位置、原因、修改要求和责任人；不因个人风格或手工估字数反复退修。作者改正文、李研改图，独立文件可并行，同一article.md的修改必须串行并回读，不能互相覆盖。每轮只处理已列明的必要问题；复审不随意新增验收标准。两轮后仍不合格，明确留档为未通过，不计完成，收齐在途任务后关闭该事项，再继续新文章，不能无限卡在同一篇。

最终交付：赵审通过后，让原作者接收该审核结果，source_task_id使用赵审本次task_id，核对实际article.md、图片链接与审查记录，完成有限“最终交付核对”任务；必要修改实际保存后回读。作者把最终文件路径、图题及验收结论返回王明，这是实际结果交付，不能只写一句“已交接”。王明读取核实后才把这一篇计入已验收完成数量并close_item。同一事项只计一次，未通过、仅草稿、工具受限或未保存均不计完成。作者等待王明核验期间不再重复做原任务；空闲作者可接受另一篇。

信息反馈：每位同事为有限步骤调用report_progress，真实工具成功并核对后立即带准确evidenceCallIds更新；不能仅因生成了一段文字就称已保存。持续主任务不创建无限增长的固定步骤计划。王明在真实节点后及时checkpoint，summary写“已验收完成N篇”，必要异常另说明角色、任务、原因、已保留成果及处理方向；不能沉默或自动重做用户已停止任务。白板若没有动态累计计数能力则保留系统正常展示，不虚构已改变白板，不要求修改Office或给文章加专用代码。

在赵审核一篇时，空闲作者和周理继续其他已开放文章。持续维持最多4篇的流水线，但不为凑满数量重复派工。停止时取消整组并等待实际清理，保留已有文章和图片，不自行重新启动。
```

**能力边界。**上述“返回王明”可由子任务结果回传及主角色核验完成，但当前模型没有独立的“将成果交回主角色”场景工具，不能只凭这段提示词保证额外人物返程动画。依赖委派仍使用原`task.assigned`。白板由Host通用任务投影生成，`continuous_task checkpoint`没有修改白板的字段，故无法只凭提示词强制墙面仅显示累计篇数；本例只约束checkpoint摘要的业务计数，不声称动态白板已实现。模型仍可能偏离提示词，实际回执、工作区文件、UI与账本是验收依据。

## 停止与恢复边界

点击聊天停止按钮取消整组，等待所有子Run、网络/文件工具清理完才落终态。刷新沿用原续接，不创建第二个任务；Host重启将未完成任务记为interrupted，不自动重放写入或恢复无人值守运行。本文实现的是一次在线Run持续推进，不是持久定时调度器。

聊天保留最多38000个UTF16单元的持久摘要，到上限冻结；完整模型事实和产物仍保存原JSONL与文件。无界运行仍会增长历史数据，需要运维管理。严格“走到人物面前才开工”、左侧忙碌颜色和Office进度曲线属于未批准Rx，本轮不宣称解决；见[Office修改集中台账](office-change-requests.md)。

## 长上下文的工具链保护

原引擎压缩保留头部时会延伸到真实工具调用/结果闭合的位置，尾部继续保留原配对边界；无安全中间区就不压缩。不通过伪造工具结果或重放操作弥补历史缺口。D104曾在真实文章退修场景触发DeepSeek HTTP400，修前失败和修后验收分别保留。长期模型仍可能在写作质量、图表布局和多轮退修上耗时，提示词不是自动质量保证。

图表当前采用简单固定布局，建议节点和边标签简洁；边标签居中避免被相邻节点覆盖，真实浏览器检查实际包围盒。它不等同于任意复杂图的自动排版、照片生成或视觉语义审核。真实单次输入文章工坊已完成五角色退修、首篇六文件并自动开始下一篇，实际证据与失败记录均从本轮验证文档/外部closure定位。

## 异步委派和真实交接（r15）

`delegate_task`默认`wait_for_completion=true`保持原行为。设置false后，原子Run接受成功才返回`state=accepted`和`task_id`；这是接单，不能作为业务完成证据。用`delegation_status {task_ids:[...],wait_for:"any"}`等待至少一项终态，或all等全部；返回真实state、summary、error和原delegate_call_id。必须读取状态，失败不是完成。没有空闲工作时应等待，而不是反复查询。原角色/组许可保留到子Run实际清理，主停止仍取消全部子Run；不增加无人管理后台任务。

`continuous_task open_item/close_item`使用稳定item_id。默认max_open_items=2限制同时开放事项；这不是“只有两个Agent”，五位同事仍可跨两项工作。异步持续委派必须使用已开放work_item，第三项明确拒绝；在途事项不能关闭，已结束ID不能重开以免误重放，新的文章使用新ID。关闭表示主角色已收齐结果并作决定，不是机器对文章质量的自动证明；不合格稿可明确留档，不应在摘要宣称通过。

`source_task_id`只引用同父、同事项的已完成前序任务，发起人物从该可信记录解析。任意人物ID、跨事项依赖、未完成前序均拒绝。后续任务仍是主角色授权的原子Run；同事不会递归提高权限。Office现有visit由fromEmployeeId驱动，严格到达后开工仍受未批准R16限制；本修复不伪造到达回执。

人物卡100%表示有限执行及该任务要求的副作用步骤已完成；父业务计划另行验收。不写文件的真实文本成果不因父漏报退为0%，要求写入但缺实际证据的子计划仍待核验。短工具的真实活动会以“刚完成…；正在组织下一步”保留到下一活动，正在执行时显示读取/保存/绘图等脱敏摘要。人物原生进度曲线R22、旧任务选择R25、忙碌颜色R24仍待Office人工审核，详见集中申请台账；后端事实修复不代表这些前端限制消失。


## 人物队列与故障（r16）

给同一成员安排多项时使用`wait_for_completion=false`；接受回执的`state=accepted`表示原Run已可靠保存，也可能尚在队中。之后用`delegation_status`取真实结果。每个人严格按接受顺序处理一项，其他角色可并行；待办含执行项每人最多64、组内256，超限应收取已有结果后再安排。依赖成果的交接用同父已完成的`source_task_id`，并传入实际文件/正文引用。

快照仅保留有界展示历史，完整成果仍在账本、成员详情与工作区文件。网络失败经过原有限重试后会终止本轮，正文明确显示原因；刷新仍可查到已有文字，不自动重做已完成操作。持续模式不等于断网后无限重试或崩溃后自动重放。

四篇双作者演示只将可信配置`max_open_items`设为4（默认仍2），提示词安排陈书/刘市各自写作、赵审审查，给各人排独立待办；保持`max_active_children=5`与真实全局容量。约1000字、图题与图文合稿仍写在提示词，不是Host硬编码。配置改变后重启Host才生效；不要将排队数当并发执行数。


## 无终点主目标与有限步骤的区别（D115/D116）

用户要求直到停止的持续主Run没有固定总步骤。Office投影使用真实委派及各子Run的执行/文件核验进度，不再把启动阶段固定计划重复当作整个持续目标的当前任务；原计划仍保存在Store供详情核查，不自动改成功。有限completion_condition、普通对话及有限子任务仍使用原固定计划。原历史待核验子卡保持真实状态，不能反过来把仍在调度的持续主Run标作阻塞；主Run本身的审批/资源等待、取消及失败继续明确呈现。
